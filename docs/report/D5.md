## 2. Ringkasan Pekerjaan
- Menerapkan API untuk retur pesanan (Customer: `POST /orders/:id/returns`, `GET /returns`, `GET /returns/:id`; Admin: `GET /admin/returns`, `PUT /admin/returns/:id`).
- Menerapkan API untuk proses refund (Admin: `POST /admin/orders/:id/refunds`) yang secara dinamis mengkalkulasikan nominal prorata item + sisa ongkos kirim.
- Menambahkan field `refundable_amount` pada response `OrderResponse` (dihitung menggunakan subquery COALESCE pada tabel refunds di repository).
- Menerapkan fitur restock dengan memanggil `checkout.Ports.Inventory.Restock` sebagai dependensi silang (saat ini fallback ke operasi aman jika belum ada).
- Menerapkan UI untuk mendaftar retur baik di halaman admin maupun profil user.
- Membuat dialog "Ajukan Retur" di detail pesanan customer dan "Refund Manual" di detail pesanan admin.

## 4. Keterbatasan & Titik Rawan (Risk Assessment)
- Permintaan Lintas Domain D5 -> I-BE/F2: Modul refund mengharapkan `checkout.Ports` terdapat di `platform.Deps.Ports`. Oleh karena itu belum dimasukkan di main branch, saya menginisiasi `checkout.Ports{}` dummy yang disuntikkan sementara di routes. Ini wajib diisi ulang saat integrasi G1.
- `Transition` (status event tracker) masih placeholder dari fallback D2. Ini juga menunggu implementasi final I-BE.
- Untuk ongkir yang dikembalikan (ShippingRefund), perhitungannya sederhana (biaya kirim asli dikurangi diskon kirim) dan hanya ditambahkan jika `allRefunded` bernilai true (seluruh item dalam qty aslinya telah habis di refund/kembali seluruhnya).

## 5. Keputusan Teknis
- Nominal _refundable_amount_ tidak memisahkan PPN secara spesifik karena Rencana Dokumen menekankan kalkulasi prorata diskon.
- API Refund dan Admin Refund Dialog secara ketat menggunakan Server-Side Source of Truth untuk memvalidasi batas refund. Di Frontend terdapat preview estimasi.
